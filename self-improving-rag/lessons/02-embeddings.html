Lesson 2: Embeddings & Vector Store

Orientation

Why are we learning this? Chunking is useless without embeddings — a chunk's embedding is its fingerprint in vector space. The vector store (Chroma) is where those fingerprints live and where retrieval searches against them. The self-improving loop creates a new collection per config version, so understanding how embeddings and collections work is essential to understanding version isolation.

How does it work? Text → embedding model → 256-dimensional vector → stored in Chroma collection → query embedding → cosine search → top-k matches.

Input → Output: ["hello world"] → [0.12, -0.03, 0.45, ...] (256 floats) → stored in Chroma → retrieved by similarity search.

What breaks without it? No embeddings = no vector search = no retrieval = no RAG. The pipeline stops at chunking.

1. Embeddings

Context Card

What it isA function that maps text to a dense vector (list of floats)
Problem solved"How do we represent text so a computer can compare meaning?"
Input → Output["hello world"] → [0.12, -0.03, 0.45, ..., 0.08] (256 floats)
OwnsCalling the embedding API, returning vectors
Does NOT ownChunking, storage, search

How It Works

We use the EURI API (OpenAI-compatible) with text-embedding-3-small at 256 dimensions:

from embeddings import EmbeddingClient

client = EmbeddingClient()  # uses EURI API, text-embedding-3-small, 256 dims

vecs = client.embed(["hello world", "goodbye world"])
print(len(vecs))
# → 2

print(len(vecs[0]))
# → 256

print(vecs[0][:5])
# → [0.012, -0.034, 0.089, 0.156, -0.021]

State Map

BEFORE:  ["hello world", "goodbye world"]  (2 strings, raw text)
         ↓ EmbeddingClient.embed() → EURI API call
         ↓ API returns 256-dimensional vectors per string
AFTER:   [[0.012, -0.034, 0.089, ...],   # "hello world"
          [-0.045, 0.067, 0.112, ...]]   # "goodbye world"
         (each vector is a point in 256D space)

Production note: If you have more than 2048 inputs, you need to chunk the list into batches of 2048 and call embed() multiple times. Our semantic chunker does this implicitly because a single document rarely has more than ~500 sentences.

ML/DL Intuition

An embedding model is a neural network trained to put semantically similar texts close together in vector space. "hello world" and "hi there" will have vectors with high cosine similarity (~0.85). "hello world" and "the stock market crashed" will be far apart (~0.15). The 256 dimensions are learned features — not human-interpretable, but collectively they encode meaning, syntax, and context.

Why 256 dimensions?

OpenAI's text-embedding-3-small supports up to 3072 dimensions. We use 256 because: (1) smaller = faster storage and search, (2) for chunk-level retrieval, 256 dims captures enough signal, (3) cost is lower. This is a config knob in config.py.

2. Chroma Vector Store

Context Card

What it isA local vector database that stores embeddings and supports similarity search
Problem solved"Given a query embedding, which stored chunk embeddings are most similar?"
Input → Outputquery(query_vec, k=5) → {documents, distances, metadatas, ids}
OwnsCollection creation, upsert, query, count, delete
Does NOT ownEmbedding generation, chunking, ranking logic

Versioned Collections

Each config version gets its own collection. This is the version isolation pattern:

rag_v1_fixed_256       ← baseline: fixed_size, chunk_size=256
rag_v2_recursive_512   ← trial 1: recursive_split, chunk_size=512
rag_v3_semantic_0.5    ← trial 2: semantic, threshold=0.5

When the optimizer applies a new config, it creates a new collection, re-chunks, re-embeds, and searches against that. Old collections stay on disk — that's the immutable version concept. You can delete them later for cleanup.

How It Works

from vector_store import ChromaStore

# Create a versioned collection
store = ChromaStore("rag_v1_fixed_256")

# Upsert chunks (IDs, embeddings, metadata, text)
store.upsert(
    ids=["chunk_000", "chunk_001", "chunk_002"],
    embeddings=[[0.1, ...], [0.2, ...], [0.3, ...]],
    metadatas=[{"source": "book.txt", "chunk_index": 0}, ...],
    documents=["Embeddings map text...", "Vector similarity...", ...]
)

print(store.count())
# → 3

# Query: find top-2 most similar chunks to this query vector
results = store.query(query_embedding=[0.15, ...], k=2)
print(results["documents"])
# → [["Embeddings map text...", "Vector similarity..."]]
print(results["distances"])
# → [[0.12, 0.28]]  (cosine distance — lower = more similar)

State Map

BEFORE:  Empty collection "rag_v1_fixed_256"
         ↓ upsert(ids, embeddings, metadatas, documents)
         ↓ Chroma stores: id→embedding, id→metadata, id→document
AFTER:   Collection contains 3 chunks, each with:
         - embedding (256D vector)
         - metadata {"source": "book.txt", "chunk_index": N}
         - document text (the actual chunk string)
         ↓ query(query_vec, k=2)
         ↓ Chroma computes cosine distance to all 3 embeddings
         ↓ returns top-2 sorted by distance (lowest first)
RESULT:  {documents: [...], distances: [0.12, 0.28], metadatas: [...], ids: [...]}

ML/DL Intuition

Chroma uses HNSW (Hierarchical Navigable Small World) for approximate nearest neighbor search. Instead of comparing the query to every single embedding (O(n)), HNSW builds a graph of connections between vectors and navigates it efficiently. The hnsw:space: cosine metadata tells Chroma to use cosine distance. This is why retrieval is fast even with thousands of chunks.

Retrieval Scoring with Keywords

When we evaluate retrieval quality (precision@k, recall@k), we need to know which chunks are "relevant." In production systems with curated golden datasets, this is done with exact chunk IDs. But in our project, chunk IDs change with every config version:

Query: "How do embeddings work?"
  fixed_size v1 → relevant IDs: ["fixed_book_0042", "fixed_book_0108"]
  recursive v2  → relevant IDs: ["recursive_book_0015", "recursive_book_0033"]
  semantic v3   → relevant IDs: ["semantic_book_0007", "semantic_book_0019"]

Instead, we use keyword-based scoring: each ground truth query comes with keywords. A retrieved chunk is "relevant" if it contains at least one keyword. This is strategy-agnostic — the same keywords work across all chunking strategies and versions.

# Ground truth: ("How do embeddings work?", "...", ["embedding", "vector", "semantic"])
# Retrieved chunks: [{"text": "Embeddings map text to vectors...", "score": 0.87}, ...]
# Check: does chunk text contain any keyword?
# → chunk 0: contains "embeddings" + "vectors" → RELEVANT
# → chunk 1: contains neither → NOT RELEVANT
# precision@5 = relevant_chunks / 5

This is sufficient for the self-improving loop because we compare relative performance (v1 vs v2 vs v3), not absolute precision. The same keywords are used for all versions — fair comparison.

Quiz

  1. What does the EmbeddingClient return for a list of 5 strings?
  2. Why does each optimizer trial get its own Chroma collection?
  3. What does hnsw:space: cosine mean in the collection metadata?
  4. If you upsert 100 chunks and query with k=5, how many results do you get?
  5. What happens if you try to upsert a 384-dim vector into a collection that already has 256-dim vectors?
Reveal answers
  1. A list of 5 vectors, each 256 floats: [[...], [...], [...], [...], [...]]
  2. Version isolation — each config version's chunks are separate. Trials don't pollute each other. Rollback is just "use the old collection."
  3. Chroma should use cosine distance (angle between vectors) for similarity, not Euclidean (L2) or dot product. Cosine is standard for text embeddings.
  4. Exactly 5 (or fewer if the collection has fewer than 5 chunks). k is the max results.
  5. Chroma will reject the upsert with a dimension mismatch error. All embeddings in a collection must have the same dimensionality.

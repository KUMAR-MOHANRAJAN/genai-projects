Lesson 1: Chunking Strategies

Orientation

Why are we learning this? Chunking is the single highest-leverage knob in a RAG pipeline. Change chunk size by 100 tokens and retrieval quality can swing 30%. The self-improving loop you'll build later diagnoses chunking failures (F-01 retrieval miss, F-02 overflow, F-03 hallucination) and proposes config deltas. You can't understand the loop without understanding what each chunker does.

How does it work? Split a document into smaller pieces. Each piece gets its own embedding. Retrieval matches the query against chunk embeddings, not whole documents.

Input → Output: One long text string → list of shorter text strings (chunks).

What breaks without it? Embedding an entire book gives one vector that matches everything equally — retrieval is useless. No chunks, no search, no RAG.

1. Why Chunking Matters

You can't embed an entire 500-page book as one vector. Even if you could, retrieval would be useless — a query about "tax deductions" would match the whole book equally.

Chunking breaks documents into smaller units. Each chunk gets its own embedding, and retrieval returns the most relevant chunks rather than whole documents.

Small chunks (~128 tokens) Large chunks (~1024 tokens)
Precision High — hits the exact passage Low — includes surrounding noise
Recall Low — may miss broader context High — captures surrounding context
Semantic usefulness May be too fragmentary to answer Self-contained, more likely to answer

2. The Three Strategies We Use

2A. Fixed-Size Token Chunking

Split every N tokens using tiktoken. With overlap, start each new chunk chunk_size - overlap tokens into the previous one.

text = "The quick brown fox jumps over the lazy dog. " * 20
chunks = fixed_size_chunk(text, chunk_size=256, overlap=0)
print(len(chunks))
# → 4

print(chunks[0][:80])
# → "The quick brown fox jumps over the lazy dog. The quick brown fox jumps over..."

State map:

BEFORE:  "The quick brown fox jumps over the lazy dog. " × 20  (one string, ~960 chars)
         ↓ tiktoken.encode() → [40, 5171, 956, ...]  (token IDs)
         ↓ slice [0:256], [256:512], [512:768], [768:960]
AFTER:   [chunk_0 (256 tok), chunk_1 (256 tok), chunk_2 (256 tok), chunk_3 (192 tok)]

Pros: Simple, predictable, fast. No embedding calls needed.
Cons: Cuts sentences mid-thought. Blind to meaning.

When it fails: A key concept straddles a token boundary — neither chunk captures the full idea. The diagnoser flags this as F-01 Retrieval Miss (all chunk similarity scores < 0.30).

2B. Recursive Character Splitting

Try to split on increasingly granular natural separators: \n\n → \n → . → . If a piece is still too large, move to the next separator.

text = """Paragraph one about embeddings.

Paragraph two about transformers. It has multiple sentences.
Each sentence is a natural boundary."""

chunks = recursive_split_chunk(text, chunk_size=50, overlap=10)
print(chunks)
# → ['Paragraph one about embeddings.',
#    'Paragraph two about transformers.',
#    ' It has multiple sentences.',
#    'Each sentence is a natural boundary.']

State map:

BEFORE:  "Paragraph one...\n\nParagraph two...\nEach sentence..."  (one string)
         ↓ split on \n\n → ["Paragraph one...", "Paragraph two...\nEach sentence..."]
         ↓ split on \n  → ["Paragraph two...", "Each sentence..."]
         ↓ merge pieces up to chunk_size=50 chars
AFTER:   ["Paragraph one about embeddings.",
          "Paragraph two about transformers.",
          " It has multiple sentences.",
          "Each sentence is a natural boundary."]

Pros: Respects document structure without embedding computation. Good default.
Cons: Character-based (not token-based). Assumes consistent formatting.

When it fails: A concept spans two paragraphs and gets split — each chunk has half the story. The diagnoser flags this as F-04 Answer Incomplete.

2C. Semantic Chunking

Embed every sentence individually. Track the running "topic centroid" (average vector). When a new sentence's cosine similarity to the centroid drops below threshold, that's a topic shift — cut there.

text = "Transformers use attention. Attention weighs tokens.
        Dogs are mammals. Cats are also mammals."

sentences = ["Transformers use attention.", "Attention weighs tokens.",
             "Dogs are mammals.", "Cats are also mammals."]
vecs = embed_fn(sentences)  # [[0.1, 0.2, ...], [0.1, 0.2, ...], [0.8, 0.1, ...], ...]

# Cosine similarity between adjacent sentences:
# [0.92, 0.35, 0.88]
#          ↑ split here (0.35 < threshold 0.5)

chunks = semantic_chunk(text, embed_fn, threshold=0.5)
print(chunks)
# → ["Transformers use attention. Attention weighs tokens.",
#    "Dogs are mammals. Cats are also mammals."]

State map:

BEFORE:  "Transformers use attention. Attention weighs tokens. Dogs are mammals. Cats are also mammals."
         ↓ _split_sentences() → 4 sentences
         ↓ embed_fn(sentences) → 4 vectors (each ~256 dims)
         ↓ _find_boundaries(): compare adjacent sentence vectors
         → similarity drops at sentence 2→3 (0.35 < 0.5 threshold)
AFTER:   ["Transformers use attention. Attention weighs tokens.",
          "Dogs are mammals. Cats are also mammals."]

Pros: Respects topic boundaries naturally. Cuts where meaning shifts, not where counters run out.
Cons: Expensive — one embedding call per sentence. Uneven chunk sizes. Threshold is another hyperparameter.

When it fails: Threshold too loose (0.3) — unrelated sentences get grouped together, the LLM confabulates connections. The diagnoser flags this as F-03 Hallucination (faithfulness < 0.50).

3. Chunk Overlap

Overlap prevents splitting a concept across two chunks where neither chunk alone suffices.

Without overlap:
  Chunk 1: "...the key principle is that"
  Chunk 2: "reliability comes from redundancy..."

With overlap (64 chars):
  Chunk 1: "...the key principle is that reliability comes..."
  Chunk 2: "...that reliability comes from redundancy..."

Rule of thumb: Overlap = 10–20% of chunk size. More overlap = more embedding compute, more near-duplicate chunks. Less overlap = potential semantic breakage.

4. How the Optimizer Uses These

Each chunking strategy triggers a different diagnosis, which maps to a different improver recipe:

FailureDiagnosisImprover's fix
fixed_size cuts mid-conceptF-01 Retrieval Missincrease k, switch to hierarchical, add overlap
recursive_split splits across paragraphsF-04 Answer Incompleteincrease chunk_size, increase overlap
semantic threshold too looseF-03 Hallucinationstricter prompt, smaller chunks, more overlap

This is why 3 strategies is the right number — each teaches a different failure mode and a different fix. Adding more strategies would just add noise.

Quiz

  1. Which chunking strategy requires computing embeddings for every sentence?
  2. What problem does chunk overlap solve?
  3. If a query returns chunks with all similarity scores < 0.30, which diagnosis fires?
  4. Why is fixed_size token-based while recursive_split is character-based? What does that mean for consistency?
  5. What is the precision-recall tradeoff between small and large chunks?
Reveal answers
  1. Semantic chunking — it embeds each sentence, then groups by cosine similarity thresholds.
  2. It prevents a concept from being split across chunk boundaries where neither chunk alone contains the full meaning.
  3. F-01 Retrieval Miss — the retrieval system found nothing relevant.
  4. Fixed_size uses tiktoken (same tokenizer as the LLM), so chunk boundaries align with the LLM's vocabulary. Recursive_split uses len(text) which counts characters — a 256-char chunk could be 40-60 words depending on the text, while 256 tokens is roughly 190 words. This means context_assembly.py (which uses tiktoken) and recursive_split use different units, causing slight mismatches.
  5. Small chunks: high precision (exact match) but low recall (miss context). Large chunks: high recall (captures context) but low precision (includes noise).

Production Grounding

In production, you don't choose one strategy — you layer them:

  1. Parse: Extract text per format (PDF→text, Markdown→headers+text)
  2. Split: Use recursive char splitting as primary, semantic splitting as fallback
  3. Enrich: Attach metadata (source, section, page, date)
  4. Embed: Generate one embedding per chunk
  5. Index: Store in vector DB with metadata for filtering

The chunk is your retrieval unit — it determines what the retriever returns. But what you retrieve and what you show the LLM are often different things (parent-child expansion, context assembly).

Lesson 4: Generation & Context Assembly

Orientation

Why are we learning this? Retrieval finds the right pages, but the LLM can only read a limited amount. Context assembly decides which chunks fit in the budget. Generation turns those chunks into an answer. The self-improving loop diagnoses F-02 (Context Overflow) when assembly truncates too much, and F-03 (Hallucination) when generation invents facts.

How does it work? Two steps: (1) pack chunks greedily by score until token budget is full, (2) call the LLM with a grounded prompt.

Input → Output: ([{text, score}, ...], max_tokens=4000) → "chunk1\n\nchunk2\n\nchunk3" → "Embeddings represent meaning by..."

What breaks without it? No assembly = LLM gets raw chunk list (wrong format). No generation = no answer. Wrong prompt = hallucination.

1. Context Assembly

Context Card

What it isGreedy-fill chunks by score into a single string within the LLM's token budget
Problem solved"How much of the retrieved context can the LLM actually read?"
Input → Output[{text, score}, ...] → "chunk1\n\nchunk2" (≤4000 tokens)
OwnsToken counting (tiktoken), sorting by score, truncation
Does NOT ownRetrieval, generation, evaluation

How It Works

from generation import assemble_context

chunks = [
    {"text": "Embeddings map text to vectors...", "score": 0.87},
    {"text": "Vector similarity measures meaning...", "score": 0.72},
    {"text": "The stock market crashed today.", "score": 0.15},
]

context, token_count = assemble_context(chunks, max_tokens=4000)

print(token_count)
# → 530  (both high-scoring chunks fit)

print(context[:80])
# → "Embeddings map text to vectors...\n\nVector similarity measures meaning..."

State Map

BEFORE:  [
           {"text": "Chunk A (200 tok)", "score": 0.87},
           {"text": "Chunk B (150 tok)", "score": 0.72},
           {"text": "Chunk C (180 tok)", "score": 0.65},
           {"text": "Chunk D (3800 tok)", "score": 0.50},
         ]
         max_tokens = 4000
         ↓ sort by score desc → [A, B, C, D]
         ↓ add A: 200 tok (total: 200)
         ↓ add B: 150 tok (total: 350)
         ↓ add C: 180 tok (total: 530)
         ↓ add D: 3800 tok → 530 + 3800 = 4330 > 4000 → STOP
AFTER:   "Chunk A\n\nChunk B\n\nChunk C"  (530 tokens)
         Returns: (context_string, 530)

Why Greedy Fill?

AutoRAG's compressor uses the same pattern: sort by score, add until budget is full. This maximizes the quality of included chunks — the highest-scoring (most relevant) chunks get priority. It's simple, fast, and effective.

2. Generation

Context Card

What it isCall the LLM with a grounded prompt containing context + question
Problem solved"Given these pages, what's the answer?"
Input → Output(context, question) → {answer, cost, tokens, latency}
OwnsLLM API call, prompt rendering, response parsing, cost/latency tracking
Does NOT ownRetrieval, context assembly, evaluation

How It Works

from generation import generate

result = generate(
    context="Embeddings map text to dense vectors...",
    question="How do embeddings represent meaning?",
    prompt_version="v1",
)

print(result["answer"][:100])
# → "Embeddings represent meaning by mapping words or sentences into dense numerical vectors..."

print(result["cost_usd"])
# → 0.000312

print(result["latency_ms"])
# → 420

The Prompt is the Control Surface

The prompt template is the single most important control surface in the pipeline. Two versions:

v1 (standard):
  "Answer based ONLY on the Context below.
   If the Context does not contain enough information, say:
   'I don't have enough information...'"

v2 (stricter — used by improver's F-03 playbook):
  "Every claim in your answer MUST be directly supported by a sentence in the Context.
   Do not add information not present in the Context."

Switching from v1 to v2 is one of the improver's recipes for fixing hallucination (F-03). The prompt is a config knob, not hardcoded text.

Token Counting — Local, Not an API Call

The assemble_context function counts tokens using tiktoken — OpenAI's official tokenizer library. This is purely local: no API call, no cost, no network:

import tiktoken
enc = tiktoken.get_encoding("o200k_base")  # loads a local lookup table (~1MB)
tokens = enc.encode("hello world")          # local computation, zero cost
print(tokens)
# → [15330, 1917]  (integer IDs, not a model call)

# How many tokens in a chunk?
text = "Embeddings map text to dense vectors."
print(len(enc.encode(text)))
# → 8  (8 tokens, not 8 characters)

tiktoken is a lookup table, not a model. It splits text into subword units and maps them to integer IDs using a pre-shipped vocabulary file. The only thing that costs money is the actual LLM API call in generator.py.

Cost Accounting

cost = (input_tokens / 1M) × $0.15 + (output_tokens / 1M) × $0.60
     = (180 / 1M) × 0.15 + (45 / 1M) × 0.60
     = $0.000027 + $0.000027 = $0.000054

Prices are constants in config.py. The unified score's cost penalty uses this value.

3. Retrieval Metrics (Keyword-Based, NO LLM Call)

Before evaluating the answer, we measure how well retrieval performed. If retrieval returns junk, the LLM gets wrong context — but we still evaluate the answer (AutoRAG's pattern: never skip evaluation, the diagnoser needs all metrics).

Precision@k

"Of the top-k chunks retrieved, how many were actually relevant?"

# Ground truth keywords: ["embedding", "vector", "semantic", "similarity"]
# Retrieved 5 chunks:
  Chunk 0: "Embeddings map text to vectors..."     ← has "embedding" + "vectors" → RELEVANT
  Chunk 1: "Vector similarity measures meaning..."  ← has "vector" + "similarity" → RELEVANT
  Chunk 2: "Dogs are mammals that bark."            ← has none → IRRELEVANT
  Chunk 3: "Semantic fragmentation is a problem."   ← has "semantic" → RELEVANT
  Chunk 4: "The stock market crashed."              ← has none → IRRELEVANT

  Precision@5 = 3/5 = 0.60  (60% of retrieved chunks were relevant)

Recall@k

"Of all the keywords that should be found, how many did we actually find?"

# Keywords: ["embedding", "vector", "semantic", "similarity", "dense"]
# Found in retrieved chunks: "embedding", "vector", "semantic", "similarity"
# Missing: "dense"

  Recall@5 = 4/5 = 0.80  (we found 80% of the expected keywords)

Retrieval Score (AutoRAG's recipe)

Retrieval = 0.5 × Precision@k + 0.5 × Recall@k
          = 0.5 × 0.60 + 0.5 × 0.80
          = 0.70

This feeds directly into the unified score as the Recall term (0.25 × retrieval). Bad retrieval naturally drags the score down — no early exit needed.

Why no early exit?

AutoRAG computes ALL metrics regardless of retrieval quality. Why? The diagnoser needs the full picture to classify failures:

  • F-01 Retrieval Miss: low precision + low recall + low faithfulness
  • F-03 Hallucination: high precision + high recall + low faithfulness

If we skipped evaluation when retrieval is bad, we couldn't tell these apart.

4. LLM-Judge Evaluation (AutoRAG's Exact Formula)

The pipeline doesn't just generate an answer — it grades it using the same LLM-judge recipes as AutoRAG. Three judges, each asking a different question:

Faithfulness Judge

"Break the answer into individual claims. Is each claim supported by the context?"

# Judge prompt:
"Step 1: Break the ANSWER into individual atomic claims.
 Step 2: For EACH claim, determine if it is verifiable from the CONTEXT.
 Step 3: Return faithfulness = supported_claims / total_claims."

# Example:
Answer: "Embeddings map text to vectors. Dogs bark."
Context: "Embeddings map text to dense numerical vectors."

Claims: ["Embeddings map text to vectors", "Dogs bark"]
Supported: [true, false]
Faithfulness: 1/2 = 0.50

Relevance Judge

"Does the answer address the question asked?"

# Judge prompt:
"Score 1.0 if the answer directly addresses the question.
 Score 0.0 if the answer is about a different topic."

# Example:
Question: "How do embeddings work?"
Answer: "Embeddings represent meaning by mapping words to vectors."
→ Score: 0.95 (directly addresses the question)

Correctness Judge (only if ground truth exists)

"Does the answer match the expected answer?"

# Judge prompt:
"Score 1.0 if the answer conveys the same information as the expected answer.
 Score 0.0 if the answer contradicts or misses the key facts."

# Example:
Expected: "Embeddings map text to dense vectors where similar texts have similar representations."
Answer: "Embeddings represent meaning by mapping words to vectors where similar words are close."
→ Score: 0.90 (conveys the same core idea)

The Unified Score Formula (AutoRAG v1.2)

These three metrics combine into one score using AutoRAG's exact formula:

Recall  = avg chunk similarity (proxy for context_precision + context_recall)
Quality = 0.6 × correctness + 0.4 × relevance
         (falls back to relevance alone if no ground truth)

UnifiedScore = 0.25 × Recall + 0.35 × Quality + 0.25 × Faithfulness
               − 0.10 × min(latency_ms / 3000, 1)
               − 0.05 × min(cost_usd / 0.01, 1)

# Example:
Recall = 0.72, Quality = 0.85, Faithfulness = 0.80
Latency = 1200ms, Cost = $0.0004

Score = 0.25×0.72 + 0.35×0.85 + 0.25×0.80 − 0.10×(1200/3000) − 0.05×(0.0004/0.01)
      = 0.18 + 0.2975 + 0.20 − 0.04 − 0.002
      = 0.6355

Why these weights? Quality (answer quality) weighs most at 0.35. Recall and Faithfulness tie at 0.25 each — because a confident liar is worse than an incomplete retriever. Latency and cost are penalties, not scores — being slow or expensive can only drag a good score down, never make a bad one look good.

Quiz

  1. How does assemble_context decide which chunks to include?
  2. What happens if a single chunk exceeds the token budget?
  3. Why is temperature=0.0 used in generation?
  4. What's the difference between prompt v1 and v2? When would the optimizer switch?
  5. How does the faithfulness judge work? What does it return?
  6. What is precision@k? What is recall@k? How do they differ?
  7. Why doesn't the pipeline skip evaluation when retrieval returns garbage?
  8. What is the unified score formula? Why are latency and cost penalties, not scores?
Reveal answers
  1. Sorts chunks by score descending, then adds them one by one until adding the next would exceed max_tokens. This is greedy fill — highest quality first.
  2. If it's the first chunk (no chunks selected yet), it's included anyway — no partial truncation. If other chunks are already selected, the oversized chunk is skipped.
  3. Temperature=0.0 makes generation deterministic. For evaluation, we want the same answer every time we run the same config — non-determinism would make score comparison meaningless.
  4. v2 adds "Every claim MUST be directly supported by a sentence in the Context" and "Do not add information not present." The optimizer switches to v2 when diagnosing F-03 (Hallucination) — stricter grounding reduces fabrication.
  5. The faithfulness judge breaks the answer into individual atomic claims, then verifies each claim against the context. It returns faithfulness = supported_claims / total_claims (0.0 to 1.0).
  6. Precision@k: fraction of top-k retrieved chunks that are relevant (contain at least one ground truth keyword). Recall@k: fraction of ground truth keywords found in the top-k chunks. Precision answers "how much of what I retrieved was useful?" Recall answers "how much of the useful stuff did I find?"
  7. AutoRAG computes all metrics regardless because the diagnoser needs the full picture to classify failures. Without evaluation, we can't distinguish F-01 (bad retrieval) from F-03 (good retrieval, hallucinated answer). The unified score naturally penalizes bad retrieval through the Recall term (0.25×retrieval).
  8. UnifiedScore = 0.25×Recall + 0.35×Quality + 0.25×Faithfulness − 0.10×min(latency/3000, 1) − 0.05×min(cost/0.01, 1). Latency and cost are penalties because being slow or expensive can only drag a good score down — they can never make a bad pipeline look good.

Lesson 3: Retrieval

Orientation

Why are we learning this? Retrieval is the bridge between "I have chunks in a database" and "I found the right chunks for this question." If retrieval fails, everything downstream fails — the LLM gets wrong context, generates a wrong answer, and the evaluator correctly scores it low. The self-improving loop's F-01 diagnosis ("Retrieval Miss") fires when retrieval returns nothing relevant.

How does it work? Embed the query → search Chroma for nearest vectors → return top-k chunks with similarity scores.

Input → Output: ("How do embeddings work?", k=5) → [{chunk_id, text, score, metadata}, ...] sorted by score descending.

What breaks without it? No retrieval = no context for the LLM = no answer. Or bad retrieval = wrong context = hallucination.

How It Works

from retrieval import search

chunks = search("rag_v1_fixed_256", "How do embeddings work?", k=3)

print(len(chunks))
# → 3

print(chunks[0])
# → {
#     "chunk_id": "fixed_book_0042",
#     "text": "Embeddings map text to dense numerical vectors...",
#     "score": 0.87,
#     "metadata": {"source": "book.txt", "chunk_index": 42}
#   }

print([c["score"] for c in chunks])
# → [0.87, 0.72, 0.65]  (sorted descending)

State Map

BEFORE:  query = "How do embeddings work?"
         collection = "rag_v1_fixed_256" (contains 100 chunk embeddings)
         ↓ EmbeddingClient.embed([query]) → query vector (256 floats)
         ↓ ChromaStore.query(query_vec, k=3)
         ↓ Chroma computes cosine distance to all 100 stored embeddings
         ↓ returns top-3: {ids, documents, distances, metadatas}
         ↓ Normalize: distance → score (1 - distance), flatten to list of dicts
AFTER:   [
           {"chunk_id": "fixed_book_0042", "text": "...", "score": 0.87, "metadata": {...}},
           {"chunk_id": "fixed_book_0108", "text": "...", "score": 0.72, "metadata": {...}},
           {"chunk_id": "fixed_book_0015", "text": "...", "score": 0.65, "metadata": {...}}
         ]

Score = 1 - Distance

Chroma returns cosine distance (lower = more similar). We convert to similarity score (higher = more similar):

distance = 0.12  →  score = 1 - 0.12 = 0.88  (very similar)
distance = 0.50  →  score = 1 - 0.50 = 0.50  (moderately similar)
distance = 0.90  →  score = 1 - 0.90 = 0.10  (barely related)

This makes scores intuitive: 1.0 = perfect match, 0.0 = no match. The diagnoser's F-01 trigger checks if max(chunk.score) < 0.30 — meaning even the best match is weak.

ML/DL Intuition

Cosine distance measures the angle between two vectors, not their magnitude. Two vectors pointing in the same direction have cosine distance 0 (perfect similarity), even if one is much longer. This is ideal for text: a short chunk and a long chunk about the same topic will have similar vectors regardless of length. Euclidean distance would penalize length differences unfairly.

2. Keyword-Based Retrieval Scoring

To measure retrieval quality (precision@k, recall@k), we need to know which chunks are "relevant." Since chunk IDs change with every config version, we use keywords from ground truth:

# Ground truth query:
("How do embeddings work?", "...", ["embedding", "vector", "semantic", "similarity"])

# Retrieved chunks:
[{"text": "Embeddings map text to vectors...", "score": 0.87},
 {"text": "The stock market crashed today.", "score": 0.15}]

# Check each chunk for keyword matches:
# Chunk 0: contains "embeddings" + "vectors" → RELEVANT ✓
# Chunk 1: contains none → NOT RELEVANT ✗

# precision@5 = 1/5 = 0.20 (1 relevant out of 5 retrieved)

This is strategy-agnostic — the same keywords work across fixed_size, recursive_split, and semantic chunking. The self-improving loop compares relative performance (v1 vs v2 vs v3), not absolute precision.

Quiz

  1. What does search(collection, query, k=5) return?
  2. Why do we convert distance to score (1 - distance)?
  3. If all 5 retrieved chunks have score < 0.30, which diagnosis fires?
  4. Why do we use cosine distance instead of Euclidean distance?
  5. How does keyword-based retrieval scoring work, and why not use chunk IDs?
Reveal answers
  1. A list of k dicts, each with chunk_id, text, score, and metadata, sorted by score descending.
  2. Chroma returns cosine distance (lower = more similar). Converting to 1 - distance gives a similarity score (higher = more similar), which is more intuitive: 1.0 = perfect match.
  3. F-01 Retrieval Miss — the retrieval system found nothing relevant. The improver will try increasing k, switching chunking strategy, or adding overlap.
  4. Cosine distance measures angle (direction), not magnitude. Two texts about the same topic have similar vectors regardless of length. Euclidean distance would penalize length differences, unfairly ranking short chunks higher.
  5. Each ground truth query has keywords. A retrieved chunk is "relevant" if its text contains at least one keyword. We use keywords instead of chunk IDs because IDs change with every config version — keywords are strategy-agnostic and work across all versions.
